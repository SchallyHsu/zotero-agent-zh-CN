# Antigravity 首次输出延迟检查（0.15.2.9）

2026-11-07，Windows / Node.js 24.15.0 / agy 1.5.2。用户反馈发送后等待较长时间才开始出字。

## 本地准备阶段

旧辅助程序在原生服务退出时使用 `Promise.race([closed, pause(2000)])`。服务很快退出后，未清理的计时器仍使 Node 进程保持运行；Zotero 等待进程退出，因而固定多等约 2 秒。

同一隔离会话的本机测量：旧程序两次分别在 426/434 毫秒输出结果，却到 2427/2431 毫秒才退出。清理计时器后，完整原生同步为 467 毫秒；已确认项目的本地续聊准备为 61/62 毫秒。这些是辅助程序进程耗时，不能当作模型首字延迟。

已确认的旧会话在原生 App 会话文件和项目配置均存在、目录匹配时，直接恢复原 ACP 会话；不会反复启动原生元数据服务。缺失文件、目录变更或未确认的记录仍回退到完整验证／迁移路径。一般的改名同步继续使用原生服务。

服务发现优先读取较新的记录，探测旧记录使用 1 秒上限，避免失效进程 ID 对应的无响应端口消耗正常操作的 15 秒超时。开始生成前也不再额外启动 Antigravity 名称／摘要同步，项目在预创建原生会话时已经确定，摘要同步在回复完成后执行。

## 原生日志中的长等待

现有使用日志显示，ACP 在收到提示后约 60 毫秒就将消息交给原生会话；较长间隔出现在该步骤之后。Gemini 4 Argon High 的三次记录，从原生发送消息到记录流式生成响应分别约 80.5、153.8 和 73.5 秒；Gemini 3.8 Flash High 约 7.1 秒，Claude Opus 5.5 High 约 2.9 秒。

这是既有使用记录中的观测值，各次消息与上下文不同，并非相同条件下的模型速度评测。日志无法单独区分模型思考、服务端排队和网络等待，也不等同于前端精确的首个字符时间。插件本地优化不能保证消除上述原生请求等待。

当前模型和 High 设置保留。需要更快响应时，可在插件模型／推理强度菜单中试用 Medium；速度与推理深度的取舍见 [Google 官方 effort 说明](https://antigravity.google/docs/cli/commands/effort/)。

## 验证

`npm run bench:antigravity` 使用独立 Gemini 目录测量完整原生同步和确认后续聊，不发送模型提示。`npm run test:xpi-projects` 在真实 Zotero/XPI 内检查缓存提示实际生效、保留同一原生会话 ID，并通过真实 agy ACP 恢复会话。单元检查覆盖缺失会话、项目目录变更、无响应服务探测，以及回复前不启动重复元数据同步。
